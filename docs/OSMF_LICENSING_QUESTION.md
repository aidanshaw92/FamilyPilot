**Subject:** Technical licensing question: a small app listing family venues, mixing OSM with other open sources

> Hello,
>
> We are building a small mobile and web app that lists parks, museums and family attractions in the London area. We would like to include about 150 OpenStreetMap features (for each: name, a category we assign, position and, where tagged, website) alongside venues taken from other open sources: Ordnance Survey OpenData (Open Government Licence) and Wikidata (CC0). We have read the ODbL 1.0, the Collective Database, Horizontal Map Layers, Substantial and Produced Work guidelines, and the attribution guidelines, and want to be sure we have understood them. We would be grateful for the Foundation's view on four points.
>
> 1. **Share-alike.** We would hold the OSM-derived features in one file in a public repository, with the ODbL notice and the OSM credit, and the app would show "© OpenStreetMap contributors" and the ODbL notice. Do you agree that publishing that file with the notice satisfies the share-alike and access conditions for what we extract?
> 2. **Mixing sources.** Our understanding of the Collective Database and Horizontal Map Layers guidelines is that, for a given type of feature in a region (say museums in London), the data should be either all from OSM or all from non-OSM sources, and that other sources may supply other properties only if they are consistently OSM or consistently not. If we serve museums only from OSM, parks only from Ordnance Survey and Wikidata, and so on, never mixing sources within one type in the same area, is that consistent with the guidelines?
> 3. **Switching a category.** When we change a category from another source to OSM, we would do it in a single release, so that at no time are both served for that type. Is that enough, or does the earlier period matter?
> 4. **Joining by identifier.** We will not keep any table that links an OSM feature to an identifier from another database. Is anything else in what we describe a "reference" that would make a non-OSM dataset not independent?
>
> We understand your reply is guidance and not legal advice. Thank you for your time.
