Verified by simulating it in a scratch worktree (nothing pushed): squash-merging #196 into `main`, then merging #197 gives **two

2. Run canary sections 1 to 6 and 8. If anything fails: Promote the recorded deployment, stop.
3. GitHub retargets #197 to `main`. Merge `main` into the #197 branch (no rebase), resolve the two conflicts as above, push,
   wait for CI (capture, build-and-test, privilege-model, Preview).
4. Merge #197 (squash). Record the #196 production deployment as its rollback target.
5. Run canary section 9 and re-check section 8. Then your iPhone pass with your own account.

**Option B, one release:** merge #197 into #196's branch first (its base), then squash-merge #196 once, run sections 1 to 6, 8
and 9 together. One deploy, one rollback, no conflict, but #196 and #197 cannot be told apart if something fails.

Rollback for either option: Promote the recorded previous deployment in Vercel (about a minute; no data migration). Then revert
the squash commit with a pull request after you approve it. Connections made during the canary keep working under the old build.
