# P0 Venue Source Integrity — root cause, invariant, and plan

Status: **Phases 1–3 complete (investigation, reproduction, design). No fix implemented yet, no
production data changed.** This document is the gate before implementation.

The baseline (`docs/VENUE_INTELLIGENCE_BASELINE.md`, merged as `7c42255`) established that of 223
usable facts FamilyPilot serves, only 55 have a source structurally tieable to the venue. It could
not say *why*. This does.

---

## Phase 1 — The data path, and where venue identity is lost

| # | stage | module | what happens to venue identity |
| --- | --- | --- | --- |
| 1 | source discovery | `source-discovery.js` `discoverSourceUrls` | **created correctly** — the seed URL is `place_records.website`, which is venue-specific |
| 2 | candidate expansion | `source-discovery.js` `mergePageCandidates` | **LOST** — see below |
| 3 | fetch | `source-fetcher.js` | URL only; no venue in scope |
| 4 | extraction | `evidence-extractor.js` | operates on text; no venue in scope |
| 5 | evidence persistence | `evidence-store.js` `saveEvidenceRecord` | **fabricated** — the row is stamped `familypilot_place_id = <crawl target>` unconditionally |
| 6 | verified bundle | `trusted-evidence.js` `verifiedBundleForVenue(id)` | **circular** — reads the stamp back and treats it as truth |
| 7 | eligibility | `trusted-evidence.js` `eligibleFact` | gates field, conflict, confidence, source *type*, excerpt length, recency, URL protocol — **never venue identity** |
| 8 | claim creation | `claims-store.js` `buildClaimRecord` | copies `sourceUrl`/`sourceType` from the evidence; venue comes from the caller |
| 9 | activation | `claims-store.js` `isClaimActive` | status, approver, expiry |
| 10 | serving | `consumer-projection.js` `getConsumerMetadata` | projects active claims for the venue |

**Identity is dropped at stage 2 and silently re-asserted at stage 5.** By stage 6 the assertion is
the only record that exists, so every later stage is reasoning from a fact nobody checked. Nothing
downstream is at fault; there is nothing left for it to validate against.

### The two mechanisms at stage 2

**(a) Link-following is bounded by host, not by venue.** `html-text-extractor.js` has exactly one
scope rule:

```js
if (resolved.hostname !== base.hostname) continue;
```

On the 16 domains carrying more than one catalogue venue, that is not a bound. The V&A and Tate
sites carry a global nav listing every sister site, those URLs match the `/visit` path priority and
score highly, and they are fetched and stored as evidence for the venue being crawled.

**(b) Common-path candidates are rooted at the origin.** `buildCommonPathCandidates` does
`new URL(homepageUrl).origin` and appends `/visit`, `/accessibility`, `/facilities` … — discarding
the venue's own path entirely. Crawling Tate Britain (`/visit/tate-britain`) it asks tate.org.uk for
`/visit` and `/accessibility`: pages about the organisation, not the gallery.

### Measured on production (read-only)

| | |
| --- | --- |
| evidence rows | 835 |
| rows carrying a `page_title` | 549 |
| rows that left the venue's own URL subtree on the same host | **389** across **72** venues |
| rows generated by the origin-rooted common-path bug | **315** |
| rows that left the host entirely | 6 |

"Left the venue's subtree" is the population the prevention fix must bound. It is **not** a
contamination count: many are legitimately shared organisation pages.

### The signal already being thrown away

`venue_source_evidence.page_title` is populated on every row on the affected hosts, and it already
names the venue correctly:

| stored against | source page | `page_title` |
| --- | --- | --- |
| Tate Britain | `tate.org.uk/visit/tate-liverpool` | `Tate Liverpool + RIBA North \| Tate` |
| Tate Modern | `tate.org.uk/visit/tate-liverpool` | `Tate Liverpool + RIBA North \| Tate` |
| Victoria and Albert Museum | `vam.ac.uk/wedgwood/visit` | `Visit V&A Wedgwood Collection` |
| V&A East Storehouse | `vam.ac.uk/east/museum/visit` | `Visit V&A East Museum` |

The page said whose it was, in a column we write on every fetch, and nothing ever read it.

## Phase 2 — Reproduction

`familypilot/src/__tests__/venue-source-integrity-repro.test.ts`, 16 tests, replaying the real crawl
from `docs/snapshots/venue-source-integrity-2026-09-26/` (48 rows, md5
`727f04b3837545b1c6d0c1ead63f4f09`).

These are **characterisation tests**: they assert what the code does *today*, so the defect is
versioned rather than argued about. The fix inverts them in the same commit, which puts the
behaviour change in the diff. They cover:

- the origin-rooted candidate generator, on Tate Britain and the V&A, and the case where it is
  harmless (a venue that owns its whole host);
- link-following selecting `tate-liverpool` into the fetch queue while crawling Tate Britain, and
  the single hostname rule that is the whole of the crawl's scope;
- the absence of any subject-of-page column in `evidence-store.js` and of any venue check in
  `eligibleFact`;
- the three named failures, each with the page title that contradicts the venue;
- **counter-examples the fix must not break**, which is why they are in the same file.

## Phase 3 — Proposed invariant

### What identity we already have

- `place_records`: `familypilot_place_id`, `external_id`, `provider`, `website`, `name`.
- `venue_source_evidence`: `familypilot_place_id` (crawl target — an assertion), `source_url`,
  `page_title`, `source_type`. **No field records what the page is about.**
- `venue_claims`: `source_evidence_id` (uuid, nullable) — a real link to the evidence row, already
  written, currently unused for validation.

So the missing thing is not an ID we have and ignore; it is a *relationship* nobody records. The
proposal adds exactly one concept and reuses everything else.

### The invariant

> Every venue-specific claim must be traceable to evidence whose relationship to that venue was
> established when the evidence was stored — and where it could not be established, the system must
> say so explicitly rather than defaulting to "belongs to this venue".

Concretely: `venue_source_evidence` gains `subject_scope`, decided at fetch time from the venue's
own `website` and the catalogue, and persisted so every consumer and audit can read it.

| `subject_scope` | rule | decision |
| --- | --- | --- |
| `venue_own_subtree` | the page is at or under the venue's own website path | eligible, identity-confirmed |
| `organisation_ancestor` | the page is a strict ancestor of the venue's own path | eligible, identity-confirmed as operator-level |
| `other_catalogue_venue` | the page is at or under **another catalogue venue's** `website` | **hard reject — never fetched, never stored** |
| `sibling_unverified` | same host, neither ancestor nor own subtree | **fail closed**: may not support a venue-specific claim unless corroborated |

Promotion out of `sibling_unverified` uses `page_title` and **only ever promotes** — it can never
turn a confirmed scope into a rejection, so a title-matching mistake cannot create contamination.

Two things this deliberately is **not**: it is not URL-slug similarity matching (the rejection rule
compares against actual catalogue `website` values — exact, ID-based), and it is not a classifier
whose output is a probability. `unestablished` from the #110 audit has no role here.

### Measured against the real crawl (all 48 rows)

| bucket | rows | correct? |
| --- | --- | --- |
| `other_catalogue_venue` (hard reject) | **8** | 8/8 genuine cross-venue. **No false positives.** |
| `venue_own_subtree` | **16** | 16/16 genuinely the venue's own page. **No false negatives.** |
| `organisation_ancestor` | 1 | correct (`/visit` for Tate Britain) |
| `sibling_unverified`, title corroborates → promoted | **3** | 3/3 genuine (RMG's per-venue accessibility pages) |
| `sibling_unverified`, no corroboration → blocked | 20 | contains **all 6 remaining** contaminated facts, plus 14 legitimate operator pages |

Together the hard reject and the fail-closed bucket prevent **all 21 contaminated facts** the
baseline found. Compare the #110 audit heuristic: 50% precision, 10 known misses.

### The open decision for review

The 20 uncorroborated siblings include 14 legitimate operator-level pages — RMG's
`/plan-your-visit/getting-here` and `facilities-access`, Tate's `/visit/accessibility` and
`/visit/families-at-tate`. Blocking them is the fail-closed choice and costs real coverage.

**Option A (recommended): block, and record.** `sibling_unverified` cannot support a venue-specific
claim. Evidence is retained, not deleted, with its scope recorded, so an audit can show exactly what
was withheld and a later corroboration rule can release it. Maximum safety; some current coverage
becomes unservable.

**Option B: serve, but never identity-confirmed.** `sibling_unverified` may support a claim, flagged
as not identity-confirmed and surfaced in the audit. Keeps coverage; leaves the Tate Liverpool and
Wedgwood facts being served to parents.

I recommend **A**, because the defect is that we cannot currently tell these apart, and B keeps
serving the exact facts we now know are wrong. **This is your call and I have not implemented
either.**

## Phases 4–6 — Plan (not started)

4. **Implement.** Scope the crawl in `source-discovery.js` (reject `other_catalogue_venue`, root
   common paths at the venue's own path); thread the venue into discovery, which today does not
   know which venue it is crawling for; persist `subject_scope` in `evidence-store.js`; enforce it
   in `eligibleFact`. Forward-only migration adding a nullable column plus a backfill; no
   destructive change. Regression test that Venue A's page cannot create a venue-specific claim for
   Venue B, plus positive controls for all 16 own-subtree rows and the 3 promotions.
5. **Audit production, read-only.** Classify every active claim into A (proven mismatch), B
   (confirmed), C (unestablished), D (legitimately shared), evidence-based, with exact counts and
   claim IDs for A, reconciled in separately written SQL.
6. **Propose repair, then stop at the mutation gate.** Least-destructive route consistent with the
   claims lifecycle, with rollback, before/after invariants, and whether recommendations change.

**No production mutation before that gate. B4 remains untouched.**
